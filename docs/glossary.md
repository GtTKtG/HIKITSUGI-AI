# 用語集

コード・仕様書・チャット上のやり取りに登場するドメイン用語を、初見の開発者が
迷わないようにまとめる。英語名はコード上の識別子（型名・関数名・カラム名）。

| 用語 | 英語名／識別子 | 意味 |
|---|---|---|
| 業務 | `Business`（`lib/schema.ts`） | 対象者が担当している仕事の単位。成果物・期限・承認ルートが異なれば別業務として分解する（同じ名前に包括しない） |
| 業務性格 / 管理系・企画系 | `business_type`: `"routine"` \| `"contextual"` | `routine`＝手順を固定的に定型化しやすい業務。`contextual`＝状況に応じて判断が変わり単一の正解手順に落とし込みにくい業務。深掘りする質問の重点を変える（`chat-system-prompt.ts`） |
| 不足項目 | `insufficient_items`（`InsufficientItemSchema`） | ある業務のヒアリングで、内容が不十分と判定された項目のキー一覧（例：`"deadline"`, `"steps"`）。AIが判定し、スコア・必須ゲートの算出元になる |
| 充足率スコア | `score` / `computeBusinessScore()` | 1業務あたりの充足度（0〜100）。AIの自己申告ではなく、`insufficient_items` から8カテゴリ・配点100点でサーバー側が決定的に算出する（`lib/scoring.ts`） |
| 必須ゲート | `mandatory_gate_missing` / `MANDATORY_GATE_ITEMS` | 期限・承認者・成果物の保存場所・システム権限・緊急時対応・権限移管のうち、未確認のものがあれば「引継未完了」とする仕組み。スコアが高くてもゲート未達なら完了扱いにしない |
| 引継完了 | `isHandoverComplete()` | 全業務が必須ゲートを満たしている状態（＝納品可能な状態）。`docs/spec.md` 2章の「納品完了の定義」に対応 |
| 未完了案件 | `UnfinishedCase`（`lib/schema.ts`） | 退職時点でまだ進行中の案件。通常の業務とは別の専用項目（目的・未決事項・主担当者・完了条件等）でヒアリングする |
| 要人間フォロー | `human_follow_up_note` | AIが3回聞き返しても不足が解消しなかった項目について、運営者・後任者が人力で確認すべき内容を記録するフィールド |
| 後任者による再現性確認 | `successor_reviews`（仕様書5.3） | 引継書完成後、後任者が業務ごとに内容を読んで「対応できる／質問がある」を記録する仕組み。質問は前任者・運営者が在籍中に回答する |
| 顧客固有コード | `access_grants` | 対象者1名＝1案件に対して発行する固有コード。`/enter/<code>` でCookieを発行し、その案件のデータのみアクセスできるようにする |
| 運営者マスターコード | `ACCESS_CODE`環境変数 | `/admin` 等、全データにアクセスできる運営者専用のログインコード |
| チャット版 / バッチ版 | `runChatTurn()` / `processInterviewTranscript()` | チャット版＝対象者とAIがターン単位で直接対話する本線。バッチ版＝文字起こし全文を一括投入する代替運用（運営者が電話等で聞き取った内容を後から構造化する用途） |
| tool use 強制 | `tool_choice: {type:"tool", name:...}` | Anthropic APIに、自然文ではなく指定したツール（構造化データ）でしか応答させない仕組み。JSON解析失敗を防ぐための設計上の要 |
| 整合性検証 | 仕様書6.4 | 全業務・未完了案件のヒアリングが終わった後、クロージング前に1回だけ行う、矛盾・欠落のチェック（頻度と開始条件の矛盾、成果物と保存場所の欠落等） |
| クロージング | 仕様書5章 | 後任者へのメッセージを聞いてインタビューを終了するステップ。ここで無限ループしないことが重要（過去に不具合があった。`runbook.md`参照） |
| 監査役（表現として廃止） | — | 旧バージョンではAIの役割を「監査役」と表現していたが、ネガティブな印象を持つ人がいるため、ユーザー向けの文言（マーケティング資料等）からは削除済み。内部設計思想としての「抜け漏れ・矛盾を検出する」役割自体は変わらない |
