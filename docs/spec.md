# HIKITSUGI AI — 開発仕様書（Claude Code引き継ぎ用）

作成日：2026年9月
本書の目的：claude.ai上での事業設計・機能設計の議論を1つにまとめ、実装フェーズ（Claude Code）にそのまま引き継ぐ

---

## 1. サービス概要

**HIKITSUGI AI**：退職・異動者にAIがインタビューし、5営業日以内に引継ぎパッケージを納品するサービス。

- ターゲット：従業員30〜300名の企業のうち、退職・異動者が発生した管理部門（経理・人事・総務・法務・経営企画等）
- 除外対象：製造現場等の技能職、従業員30名未満・300名超の企業
- 対象外の対応範囲：人事システム連携、Slack/Teams連携、複雑な権限管理、引継ぎ内容の真偽検証、引継ぎ後の継続サポート（いずれも初期スコープ外）

## 2. 「納品完了」の定義

以下5条件をすべて満たした状態を納品完了とする。

1. 業務一覧が網羅されている（成果物単位まで分解されている）
2. 各業務について5.1の確認項目（目的、頻度・実施時期、開始条件、期限、具体手順、成果物、判断ポイント、例外、失敗時対応、関係者、使用ファイル・システム、権限移管状況）が記載されている
3. 未完了案件が明記されている（5.2の項目を含む）
4. AIが検知した不足項目が、再質問により補完済み、または「要人間フォロー」として確認先・期限とともに明記されている
5. 6.5の必須ゲートをすべての業務が満たしている（＝「引継未完了」の業務が残っていない）
6. Word/PDF形式で出力され、後任者・上司が閲覧可能な状態になっている

## 3. 価格体系

| 項目 | 価格 |
|---|---|
| 通常価格 | 98,000円 / 1名 |
| モニター価格（初期3〜10件限定） | 49,800円 / 1名 |
| 複数名同時依頼 | 2名目以降10％引き、5名まで（6名目以降は個別見積り） |

- 支払い：着手時前払い（モニター初期3社のみ納品後精算を許容）
- キャンセル：AIインタビュー開始前は全額返金、開始後は原則不可（運営都合の場合を除く）

## 4. データ・セキュリティ方針

- 顧客データをモデルの学習に使用しない
- 顧客ごとにデータを分離する
- 保存期間を顧客側で選択可能にする
- 契約終了後にデータを削除可能にする

## 5. インタビュー設計（AIがチャットで直接ヒアリングする）

対象者本人が、ブラウザ上でAIと直接チャットしながらインタビューに答える。文字起こしの受け渡しは発生しない（対象者がテキストを直接入力するため）。AIは、単なる聞き取り役ではなく「引継ぎ内容の不足と矛盾を検出する監査役」として、以下の5段階で会話を進行する。引継完了の基準は「前任者が回答したこと」ではなく「後任者が、追加質問なしに、期限内に、正しい承認を得て業務を完了できること」である。

```
1. 棚卸し（担当業務群の網羅的な洗い出し）
2. 業務分解（成果物・期限・承認ルートが異なる業務は別項目として分ける）
3. 実務深掘り（業務ごとに5.1の項目を確認）
4. 整合性検証（回答全体の矛盾・欠落をAIが横断チェック）
5. クロージング（未完了案件・後任者へのメッセージ）
```

### 進行ロジック

- 業務一覧を最初に聞き出す（非定常業務・進行中案件も見落とさないよう確認する）
- 「業務全般」のような包括的な業務名は受理せず、成果物・期限・承認ルートの異なる作業は別業務として分解してから深掘りする
- 業務ごとに5.1の項目を順番に質問する
- 各回答を受け取るたびに、6章の充足判定基準をその場で適用する。「都度」「上長に確認」「所定フォルダ」「特になし」等の曖昧表現は、具体化されるまで確定回答として扱わない（6.1参照）
- 不足・曖昧と判定した項目は、その場で聞き返す（同一項目につき最大2回まで、6.4のルールをそのまま踏襲）
- 3回目でも不足が解消しない項目は「要人間フォロー」として記録し、対象者を待たせずに次の項目へ進む
- 全業務の深掘りが終わったら、クロージング前に回答全体を横断して矛盾・欠落がないか検証する（整合性検証）
- 未完了案件・クロージングまで終わったら、AIが完了を対象者に伝え、裏側で7章のJSON構造化データを生成する

### 5.1 業務ごとの確認項目（仕様変更：後任者が再現できる水準まで深掘り）

後任者が実際に業務を再現できるよう、旧仕様の8項目から以下へ拡張した。

| 項目 | 分類 | 備考 |
|---|---|---|
| 目的・対象（purpose） | 必須確認型 | 何のために・誰に向けた業務か |
| 頻度・実施時期（frequency） | 必須確認型 | |
| 開始条件（trigger） | 必須確認型 | |
| 期限（deadline） | 必須確認型 | 法定・社内期限、実務上の着手時期 |
| 具体的手順（steps） | 必須確認型 | 「最初に開くファイル」「保存先の命名規則」等、再現性を高める追質問を使う |
| 成果物・保存場所（deliverables） | 必須確認型 | 正本・テンプレート・命名規則・保存場所 |
| 判断ポイント（judgment） | 有無確認型 | 「特にない」で終わらせず、過去に迷った事例等から引き出す |
| 例外・イレギュラー対応（exception） | 有無確認型 | |
| 失敗時対応（failure） | 有無確認型 | 緊急時の初動・連絡先を含む |
| 関係者・役割（stakeholders） | 必須確認型 | 実務担当・確認者・承認者・提出者・代理者を区別する |
| 使用ファイル・システム（systems / system_details） | 必須確認型 | システムごとにURL・ID・ログイン方法・権限・端末制限・電子証明書・申請先・代理者・マニュアル保管場所・関連ファイル保存場所を聞く（下記の注意点参照） |
| 権限移管状況（access_handover） | 必須確認型 | 後任者への付与状況・前任者権限の停止日・未完了の申請 |

システム名が固有名詞で具体的に挙がっていれば「使用ファイル・システム」項目自体は
充足とみなし、URL・ID・権限等の詳細が不明であることそのものは不足判定の対象にしない。

**セキュリティ上の注意（パスワードの扱い）**：当初はパスワードの値そのものをヒアリング・
記録する運用を検討したが、依頼企業からの改善方針を受けて撤回した。**パスワードそのものは
引継書に記載せず、会社が定める安全な方法（社内パスワード管理ツール等）で別途移管する**。
ヒアリングでは代わりに、ログイン方法・権限・端末制限・電子証明書・申請先・代理者を聞く。

### 5.2 未完了案件の専用ヒアリング（仕様変更）

進行中案件は「〇〇さんが継続対応」のような一言で終わらせず、案件ごとに次を確認する。
目的・対象範囲・背景 / 現在のステータス / 未決事項・懸念事項・依存関係 / 次のアクション・
次回予定日・最終期限 / 主担当者・意思決定者・相手方の窓口 / 関連資料と最新の打合せ記録の
所在 / 放置・遅延した場合の影響 / 完了条件と完了を確認する者。

### 5.3 後任者による再現確認（将来対応・今回はスコープ外）

改善方針では、後任者が実際にファイルを開き、システムにログインし、手順・承認ルートを
説明できることの確認をもって引継完了とする案が挙げられている。これは後任者用の新しい
認証・確認画面が必要な大規模機能のため、今回のヒアリング精度改善には含めず、別途スコープを
見積もったうえで対応する。

### 将来の音声版への拡張（今回は対象外）

音声で直接ヒアリングする方式（対象者が電話・通話でAIと話す）は、タイピング負担がなくなる利点がある一方、音声認識・音声合成・通話基盤の追加開発が必要になり難易度が大きく上がる。今回はまずチャット形式で「AIが直接ヒアリングする」を実現し、対象者の離脱率等の実績を見てから拡張を判断する。

### モニター期間中の運用との関係

Phase 2で運営者が電話で聞き取っていたやり方は、このチャット版の検証が済むまでの比較対象・代替手段として並行して残してよい（7.3参照）。

## 6. 不足検知ロジック（判定基準）

### 6.1 項目の重要度分類

| 項目 | 分類 |
|---|---|
| 目的、頻度・実施時期、開始条件、期限、具体的手順、成果物、関係者、使用ファイル・システム、権限移管状況 | 必須確認型 |
| 判断ポイント・例外・失敗時対応 | 有無確認型 |

- **必須確認型**：内容が具体的でない・固有名詞を含まない・無回答の場合は「不足」
- **有無確認型**：対象者が明確に「ない」と述べていれば不足として扱わない。無回答またはすり替わりの場合のみ「不足」

### 6.2 曖昧回答の検知（仕様変更）

次の表現のみで、具体的な固有名詞・数値・手順が伴っていない場合は確定回答として扱わず、内容が具体化されるまで再質問する。対象者がどうしても具体化できない場合は、未確認事項として確認先・期限を human_follow_up_note に記録する。

| 曖昧表現 | 再質問の観点 |
|---|---|
| 都度、必要に応じて | 発生条件・年間の概算回数・直近の実施時期 |
| 上長に確認 | 上長の氏名・役職、確認内容、確認方法、代理者 |
| 所定フォルダ | チーム・チャネル・フォルダ階層・ファイル名 |
| 特になし（判断ポイント等） | 想定ケースを提示しても不要か |
| 経験なし（例外・失敗時対応） | 未経験でも発生した場合の初動・相談先 |
| 対応済み・終了済み（未完了案件） | 完了の証跡・残存作業・後続フェーズへの影響 |
| 関係者一覧（氏名の列挙のみ） | 各人の役割・責任・代理関係 |

### 6.3 承認者の検出（クロスチェック）

具体的手順の発言内に承認関連キーワード（承認・確認をもらう・決裁・相談する等）があり、かつ関係者の発言に承認者名がない場合のみ「承認者不明」と判定する。

### 6.4 整合性検証（新規）

全業務の深掘りが終わった時点で、回答全体を横断して次のような矛盾・欠落がないか確認する。矛盾や重大な欠落が残る場合、human_follow_up_note に具体的に記録する。

- 頻度と開始条件が矛盾していないか
- 期限に対して着手時期・承認日が現実的か
- 実務担当者・確認者・承認者・提出者が区別されているか
- 成果物があるのに保存場所が未記載のままになっていないか
- 使用システムがあるのに権限移管状況が未確認のままになっていないか
- 未完了案件に次回期限・責任者・完了条件があるか

### 6.5 充足率スコアと必須ゲート（仕様変更：客観採点＋必須ゲート）

自己申告的な充足率（AIが直接scoreを算出する方式）を廃止し、8カテゴリ・配点100点の客観採点に切り替えた。スコアはAIの出力を信用せず、insufficient_items からアプリ側（`lib/scoring.ts`）が決定的に算出する。

| カテゴリ | 配点 | 対応する項目 |
|---|---|---|
| 業務の目的と範囲 | 10 | purpose, trigger |
| 実施時期と期限 | 15 | frequency, deadline |
| 手順の再現性 | 20 | steps |
| 成果物と保存場所 | 15 | deliverables |
| 役割と承認ルート | 15 | stakeholders |
| 判断基準 | 10 | judgment |
| 例外・事故対応 | 10 | exception, failure |
| 権限移管 | 5 | access_handover |

カテゴリ内に複数項目がある場合は配点を項目数で均等に按分し、不足していない項目の分だけ加点する（例：「実施時期と期限」はfrequency・deadlineそれぞれ7.5点）。

**必須ゲート**：重要業務について、次のいずれかが未確認であれば、総合点にかかわらず「引継未完了」と判定する（進捗画面・出力に明示する）。

- 期限（deadline）
- 承認者・実務担当者（stakeholders）
- 成果物の保存場所（deliverables）
- システム権限（systems）
- 緊急時の初動と連絡先（failure）

現状は全業務に一律でこのゲートを適用している（「重要業務」の判定を業務ごとに設定する仕組みは未実装）。

### 6.6 再質問ルール

- 不足項目には再質問文を生成する
- 同一項目への再質問は最大2回まで
- 3回目でも不足が解消しない場合は「要人間フォロー」として運営側が個別対応する

## 7. AI処理の入出力仕様

### 7.1 会話進行のロジック（ターン単位の処理）

このシステムは、AIが1問ずつ質問し、対象者が1つずつ答える「ターン単位」の会話になる。バッチで全文を後からまとめて処理する方式（Phase 2までの方式）とは異なり、以下をターンごとに管理する必要がある。

- 現在どの業務について質問しているか
- その業務の確認項目（5.1）のうち、どれが充足済みで、どれが不足しているか
- 不足項目について、これまで何回聞き返したか（最大2回）

これらの状態は、会話履歴（それまでのやりとり全部）を毎回AIに渡すことで、AI自身に管理させる方式を基本とする。会話が長くなった場合の履歴管理（要約するか、全文を毎回渡すか）は、Claude Codeでの実装時に具体的な会話量を見ながら決める。

### 7.3 モニター期間の代替運用（並行して残す場合）

Phase 2で運用していた「運営者が電話で聞き取り→文字起こし→AIが事後構造化」という方式も、チャット版の検証期間中は並行して使えるようにしておくとよい。この場合は、claude.aiのProject custom instructionsに設定済みのプロンプト（現状Markdown出力）の出力フォーマット部分を7.2のJSON形式に差し替えるだけで流用できる。

### 7.4 バックエンドの構成（ゲートウェイ不要）

利用するAIはClaude単体のみのため、AIゲートウェイ（ルーティング・フェイルオーバー・利用量集計の中継層）は不要と判断。以下のターン単位の直接呼び出し構成とする。

```
対象者のチャット入力
  → バックエンドサーバー（会話履歴を保持、APIキーを保管、ターンごとにClaude APIを呼び出す）
    → Anthropic API（Claude呼び出し）
  → 次の質問を対象者に返す（不足していれば聞き返し、充足していれば次の項目へ）
  ↳ 全項目完了時：7.2のJSON構造化データを生成してDBに保存
→ 画面へ反映（進捗表示・引継書プレビュー）
```

- APIキーはバックエンドの環境変数にのみ保管し、フロントエンドには一切渡さない
- systemプロンプト（役割定義・5.1の質問設計・6章の判定ロジック）と、これまでの会話履歴を、ターンごとにAPIへ送信する
- 完了判定（全業務・未完了案件・クロージングが終わったか）はAI自身に判断させ、完了時に7.2のJSON出力へ切り替えさせる

## 8. Phase 3 MVP画面構成（5画面）

1. **企業管理**：会社名、担当者、対象社員
2. **AIインタビュー**：対象者本人がAIと直接チャットしてヒアリングを完了する画面。1問ずつ質問し、リアルタイムで充足を判定して聞き返す（5章・7章参照）。文字起こしのアップロード機能は不要
3. **進捗**：業務ごとの充足率スコア表示（例：業務把握100％、判断基準70％、例外対応40％）
4. **引継書プレビュー**：本人が修正可能な形で表示
5. **出力**：Word / PDF

初期スコープ外：人事システム連携、Slack連携、Teams連携、複雑な権限管理、音声によるヒアリング（将来検討）

## 9. 運用フロー（モニター期間・想定4〜5営業日モデル）

チャット版AIインタビューにより、従来のDay1（面談）とDay2（不足検知・再質問）が1回のセッションに統合される見込みである。

| 営業日 | 工程 |
|---|---|
| Day 0 | 事前ヒアリング・日程調整（対象者へのアクセスURL発行） |
| Day 1 | 対象者がAIチャットでインタビューを完了（不足検知・再質問も同一セッション内で完結） |
| Day 2 | 人力チェック・修正 |
| Day 3 | 引継書レビュー・後任者メッセージ確認 |
| Day 4 | 納品・上司評価アンケート送付 |

この4営業日モデルは、チャット版インタビューが実際に離脱なく完了できるかを検証してから正式に採用する。検証中は、従来の5営業日モデル（Day1に運営者が電話で聞き取り、Day2で不足を確認）と並行し、KPI①面談完了率を比較する。

モニター期間（3〜10件）は運営者1名が全工程を担う。

## 10. KPI（モニター期間で計測）

| KPI | 目標値 |
|---|---|
| ① 面談完了率 | 80％以上 |
| ② 引継書修正率 | 20％以下 |
| ③ 上司評価（5段階） | 4.0以上 |
| ④ 追加質問数 | データ収集し傾向を見る |

## 11. 開発時の優先順位（Claude Codeでの実装方針）

1. まず7.1〜7.2のロジックで、対象者とAIがターン単位でチャットする最小構成を作る（DB・認証は最小限）。1問質問→回答受信→充足判定→次の質問 or 聞き返し、のループが動くことを最優先する
2. 5画面のうち「AIインタビュー（チャット）」「進捗」「引継書プレビュー」「出力」を優先する（企業管理画面は後回しでも運用可能）
3. AIゲートウェイ、外部システム連携、複雑な権限管理、音声によるヒアリングは実装しない（本書1章のスコープ外事項を厳守）
4. 顧客データの分離・保存期間設定・削除機能は、本番の顧客データを扱う前に必ず実装する（本書4章）
