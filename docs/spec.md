# HIKITSUGI AI — 開発仕様書（Claude Code引き継ぎ用）

作成日：2026年9月
本書の目的：claude.ai上での事業設計・機能設計の議論を1つにまとめ、実装フェーズ（Claude Code）にそのまま引き継ぐ

---

## 1. サービス概要

**HIKITSUGI AI**：退職・異動者にAIがインタビューし、5営業日以内に引継ぎパッケージを納品するサービス。

- ターゲット：従業員30〜300名の企業のうち、退職・異動者が発生した管理部門（経理・人事・総務・法務・経営企画等）
- 除外対象：製造現場等の技能職、従業員30名未満・300名超の企業
- 対象外の対応範囲：人事システム連携、Slack/Teams連携、複雑な権限管理、引継ぎ内容の真偽検証、引継ぎ後の継続サポート（いずれも初期スコープ外）

## 2. 「納品完了」の定義

以下5条件をすべて満たした状態を納品完了とする。

1. 業務一覧が網羅されている
2. 各業務について8項目（頻度・開始条件・具体手順・判断ポイント・例外・失敗時対応・関係者・使用ファイルシステム）が記載されている
3. 未完了案件が明記されている
4. AIが検知した不足項目が、再質問により補完済み、または「対応不可」として明記されている
5. Word/PDF形式で出力され、後任者・上司が閲覧可能な状態になっている

## 3. 価格体系

| 項目 | 価格 |
|---|---|
| 通常価格 | 98,000円 / 1名 |
| モニター価格（初期3〜10件限定） | 49,800円 / 1名 |
| 複数名同時依頼 | 2名目以降10％引き、5名まで（6名目以降は個別見積り） |

- 支払い：着手時前払い（モニター初期3社のみ納品後精算を許容）
- キャンセル：AIインタビュー開始前は全額返金、開始後は原則不可（運営都合の場合を除く）

## 4. データ・セキュリティ方針

- 顧客データをモデルの学習に使用しない
- 顧客ごとにデータを分離する
- 保存期間を顧客側で選択可能にする
- 契約終了後にデータを削除可能にする

## 5. インタビュー設計（質問フロー）

対象者へのインタビューは、以下の順で情報を収集する。

```
業務一覧の抽出
  → （業務ごとに）頻度 → 開始条件 → 具体的手順 → 判断ポイント
     → 例外・イレギュラー対応 → 失敗時対応 → 関係者 → 使用ファイル・システム
→ 未完了案件
→ クロージング（後任者へのメッセージ等）
```

Day1は音声インタビュー（運営者が口頭で質問）形式とし、Web会議の文字起こしを取得する運用とする。「対象者が直接AIチャットに入力する」形式ではない（対象者のITリテラシー差・離脱リスクを考慮した判断）。

**文字起こしの扱いについて（重要・誤解しやすい点）**：文字起こし自体は、Zoom／Teams等のWeb会議ツールが標準で備える自動文字起こし機能を利用する。この処理はHIKITSUGI AIのシステムが独自に実装する機能ではない。つまり、

- 文字起こしは「行わない」のではなく、「外部ツールの機能でDay1のうちに自動生成される」
- HIKITSUGI AIのシステム（本書8章のAIインタビュー画面）が受け取るのは、既に文字起こしされたテキストである
- したがって、システム側で音声認識・音声のテキスト化機能を新たに開発する必要はない。必要なのは、そのテキストを貼り付け・アップロードできる入力画面と、7章のAI構造化処理だけである

将来的に対象者へのヒアリング自体をAIが音声で直接行う仕組みに発展させる場合は、この前提が変わるため、着手前に別途仕様を切り直す。

## 6. 不足検知ロジック（判定基準）

### 6.1 項目の重要度分類

| 項目 | 分類 |
|---|---|
| 頻度・開始条件・具体的手順・関係者・使用ファイル | 必須確認型 |
| 判断ポイント・例外・失敗時対応 | 有無確認型 |

- **必須確認型**：内容が具体的でない・固有名詞を含まない・無回答の場合は「不足」
- **有無確認型**：対象者が明確に「ない」と述べていれば不足として扱わない。無回答またはすり替わりの場合のみ「不足」

### 6.2 承認者の検出（クロスチェック）

具体的手順の発言内に承認関連キーワード（承認・確認をもらう・決裁・相談する等）があり、かつ関係者の発言に承認者名がない場合のみ「承認者不明」と判定する。

### 6.3 充足率スコア

- 必須確認型5項目：各2点（満点10点）
- 有無確認型3項目：各1点（満点3点）
- 充足率（％）＝（獲得点合計 ÷ 13）× 100

### 6.4 再質問ルール

- 不足項目には再質問文を生成する
- 同一項目への再質問は最大2回まで
- 3回目でも不足が解消しない場合は「要人間フォロー」として運営側が個別対応する

## 7. AI処理の入出力仕様

### 7.1 現状（人力運用・Markdown出力）

claude.aiのProject custom instructionsに、文字起こしを渡すと上記6章のロジックに従って構造化するプロンプトを設定済み。現在の出力はMarkdown形式（人間が読む前提）。

### 7.2 Phase 3で必要な変更（JSON出力への切り替え）

システムに組み込む際は、以下のJSON形式で出力させるようプロンプトを改修する（プロンプトの「出力フォーマット」章のみ差し替えれば、質問設計・判定ロジック部分はそのまま流用可能）。

```json
{
  "businesses": [
    {
      "name": "業務名",
      "frequency": "頻度",
      "trigger": "開始条件",
      "steps": ["手順1", "手順2"],
      "judgment": "判断ポイント（「ない」と明言の場合はその旨）",
      "exception": "例外・イレギュラー対応",
      "failure": "失敗時対応",
      "stakeholders": [{"role": "承認者", "name": "氏名・部署", "note": "備考"}],
      "systems": "使用ファイル・システム",
      "score": 92,
      "insufficient_items": ["judgment"],
      "human_follow_up_note": "承認者未確認、または null"
    }
  ],
  "unfinished_cases": [
    {"name": "案件名", "progress": "進捗状況", "next_action": "次のアクション", "deadline": "期限"}
  ],
  "closing_message": "後任者へのメッセージ",
  "re_questions": [
    {"business": "業務名", "item": "不足項目", "question": "再質問文"}
  ],
  "interview_round": 1
}
```

### 7.3 バックエンドの構成（ゲートウェイ不要）

利用するAIはClaude単体のみのため、AIゲートウェイ（ルーティング・フェイルオーバー・利用量集計の中継層）は不要と判断。以下の直接呼び出し構成とする。

```
フロントエンド（文字起こしを送信）
  → バックエンドサーバー（APIキーを保管、systemプロンプトを付与、JSON受信）
    → Anthropic API（Claude呼び出し）
  → DB保存（業務別データ・充足率スコア）
→ 画面へ反映（進捗表示・引継書プレビュー）
```

- APIキーはバックエンドの環境変数にのみ保管し、フロントエンドには一切渡さない
- systemプロンプト（本書7.2のJSON出力指定を含む構造化プロンプト全文）と、userメッセージ（文字起こし本文＋インタビュー回数）を分けて送信する
- 再質問後の2回目・3回目の処理は、`interview_round`をインクリメントして同じ構造で再送する

## 8. Phase 3 MVP画面構成（5画面）

1. **企業管理**：会社名、担当者、対象社員
2. **AIインタビュー**：文字起こしテキストの貼り付け／アップロード画面。文字起こし自体はZoom/Teams等の外部ツールが自動生成し、運営者がその結果テキストをこの画面に入力する（システム側で音声認識・文字起こし機能を実装する必要はない。5章「文字起こしの扱いについて」参照）
3. **進捗**：業務ごとの充足率スコア表示（例：業務把握100％、判断基準70％、例外対応40％）
4. **引継書プレビュー**：本人が修正可能な形で表示
5. **出力**：Word / PDF

初期スコープ外：人事システム連携、Slack連携、Teams連携、複雑な権限管理

## 9. 運用フロー（モニター期間・5営業日モデル）

| 営業日 | 工程 |
|---|---|
| Day 0 | 事前ヒアリング・日程調整 |
| Day 1 | AIインタビュー実施（運営者同席） |
| Day 2 | 不足検知・再質問（対象者への追加確認） |
| Day 2午後〜Day3 | 人力チェック・修正 |
| Day 4 | 引継書レビュー・後任者メッセージ確認 |
| Day 5 | 納品・上司評価アンケート送付 |

モニター期間（3〜10件）は運営者1名が全工程を担う。

## 10. KPI（モニター期間で計測）

| KPI | 目標値 |
|---|---|
| ① 面談完了率 | 80％以上 |
| ② 引継書修正率 | 20％以下 |
| ③ 上司評価（5段階） | 4.0以上 |
| ④ 追加質問数 | データ収集し傾向を見る |

## 11. 開発時の優先順位（Claude Codeでの実装方針）

1. まず7.2のJSON出力プロンプトを使い、バックエンドからClaude APIを直接呼び出す最小構成を作る（DB・認証は最小限）
2. 5画面のうち「AIインタビュー入力」「進捗」「引継書プレビュー」「出力」を優先する（企業管理画面は後回しでも運用可能）
3. AIゲートウェイ、外部システム連携、複雑な権限管理は実装しない（本書1章のスコープ外事項を厳守）
4. 顧客データの分離・保存期間設定・削除機能は、本番の顧客データを扱う前に必ず実装する（本書4章）
